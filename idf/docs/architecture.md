# 架构设计

## 1. 设计目标

| 目标 | 做法 |
|---|---|
| 不阻塞 | 所有慢操作（AT、TLS、推送）都在独立任务/队列中执行，主循环无长阻塞 |
| 不丢短信 | URC 读取与 AT 事务共用一把递归锁，事务期间收到的 `+CMT` 也会转交上层 |
| 不爆内存 | 页面分块输出、TLS 动态缓冲、长短信合并用堆而非栈 |
| 好定位问题 | 统一日志（串口 + Web 200 行环形缓冲，含 `AT>` 原始交互与「AT指令」过滤）、`/decode` 诊断接口、复位原因记录 |

## 2. 分层

```
                    ┌──────────────────────────────┐
   浏览器 ── HTTP ──▶│ web        (esp_http_server) │
                    └───────────┬──────────────────┘
                                │ 调用
        ┌───────────────────────┼──────────────────────┐
        ▼                       ▼                      ▼
┌───────────────┐      ┌────────────────┐     ┌───────────────┐
│ forwarder     │◀─────│ modem          │     │ notify        │
│ 转发策略/命令  │ SMS  │ AT/PDU/长短信   │     │ 邮件 + 推送    │
└───────┬───────┘      └───────┬────────┘     └───────┬───────┘
        │                      │                      │
        └──────────┬───────────┴──────────────────────┘
                   ▼
          ┌──────────────────┐        ┌────────────────┐
          │ core 配置/日志/工具│        │ net WiFi/SNTP  │
          └──────────────────┘        └────────────────┘
```

依赖方向单向向下，禁止反向包含：

- `core`：无业务依赖，最底层；
- `net` / `notify` / `modem`：各自独立，只依赖 `core`；
- `forwarder`：依赖 `core` + `modem` + `notify`（唯一放业务策略的地方）；
- `web`：依赖 `core` + `modem` + `notify` + `net` + `sched` + `ota` + `esim`；
- `ota`：依赖 `core` + `net` + `notify` + `app_update`，只负责写分区与回滚确认（版本检查在浏览器侧）；
- `esim`：依赖 `core` + `modem`（借用 AT 串口），只负责 eUICC 的 ES10b/ES10c 与 APDU 透传；
- `main`：只做装配与启动顺序编排。

## 3. 任务模型

| 任务 | 栈 | 优先级 | 职责 |
|---|---|---|---|
| `main` | 6 KB | 1 | 启动编排，初始化完即退出 |
| `httpd` | 8 KB | 5 | 处理 HTTP 请求（长耗时请求转异步） |
| `web_async` | 6 KB | 4 | 按需创建，执行 ping/查询/AT/PDU 解码等阻塞操作；走 TLS 的（推送测试、邮件测试、自检、保号 HTTP）8 KB，发短信 10 KB |
| `esim_reset` | 3 KB | 4 | 切卡成功后延迟 2 秒软重启模组 |
| `at_reader` | 6 KB | 5 | 空闲时读串口、分发 URC |
| `modem` | 8 KB | 4 | AT 作业队列：初始化、发短信、ping、HTTP 保号访问、软/硬重启 |
| `forwarder` | 6 KB | 3 | 短信策略：黑名单、管理员命令、分发通知 |
| `notify` | 8 KB | 3 | 邮件与 HTTP 推送（TLS） |
| `heartbeat` | 4 KB | 2 | 网络/本机自检与自愈（默认 60s 一轮） |
| `netmon` | 4 KB | 3 | 4G 基站注册检测与分级自愈（默认 60s 一轮） |
| `sched` | 6 KB | 2 | 定时任务：短信 / Ping / HTTP，20 秒扫一次任务表 |
| `ota_confirm` | 3 KB | 3 | 新固件回滚确认（联网稳定 45 秒后 mark valid，仅升级后启动那次） |
| `esp_timer` | 系统 | 高 | 长短信超时检查（1s 周期） |

> **配网模式**（`net/wifi_portal.c`）只在两种情况下出现：启动时没有任何 WiFi 账号，
> 或连续 3 次连不上已保存的账号。此时不启动主 Web 服务，80 端口交给配网专用的 httpd，
> 避免两个服务器抢端口；保存账号后重启，回到「STA 连接 → 主 Web」的正常流程。
> 账号存在 NVS `sms_wifi`，优先于 menuconfig 的编译期常量。

### 4G 基站守护（netmon）

模组「注册上基站后长期不再掉线」只是理想情况：现网里会因子区重选、运营商踢网、
模组射频卡死等原因静默离线，且模组自己不会再主动注册。netmon 专门盯这件事：

| 检查（纯 AT 信令，零流量/零短信） | 判定 | 动作 |
|---|---|---|
| `AT+CREG?` / `AT+CEREG?` | 连续 2 次都不是 1/5 | 判定掉线，进入自愈 |
| `AT+CSQ` | 已注册但连续 3 次返回 99 | 判定射频卡死，进入自愈 |
| `AT+CFUN?` = 4 | 用户手动开了飞行模式 | 暂停检测，不改动射频 |
| 自愈第 1 级 | — | 飞行模式保持 10s → 20s → … → 最多 300s（TCP 式退避）后 `CFUN=1 → COPS`（自动 `COPS=0` / 手动 `COPS=1,2,"PLMN",Act`），等 90 秒注册 |
| 自愈第 2 级 | 第 1 级失败 | `AT+CFUN=1,1` 软重启后重新初始化 |
| 自愈第 3 级 | 第 2 级失败 | EN 引脚断电硬重启 |
| 三级都失败 | — | 记日志、冷却 5 分钟后从第 1 级重来 |

通知策略刻意保守：**日常掉线→重连只写日志**；只有连续 5 轮（每轮含一次飞行模式重启 + 软/硬重启）都失败
才发一次「4G 网络无法自动重连」，正文带上掉线起始时间（NTP 已同步用本地时间，
否则用设备运行时长）；此后恢复再发一条「4G 网络已恢复」，同一轮掉线不会重复轰炸。

选网配置：设备页可选自动/手动，手动需填写 PLMN 并选择 LTE/3G/2G。配置存 NVS
（`operatorMode`/`operatorCode`/`operatorAct`），模组初始化时用 `AT+COPS` 应用；
保存后重启设备生效。netmon 射频重启同样按配置重新选网，不会把手动设置覆盖成自动。

### 心跳自愈策略

心跳刻意把「设备自身挂了」和「外网断了」分开判断，避免断网时反复重启：

| 现象 | 判定 | 动作 |
|---|---|---|
| 连不上自己的 80 端口 | 连续 2 次 | `esp_restart()`：httpd 已经不可用，只能重启 |
| 外网 DNS/TCP 探测失败 | 连续 3 次 | `wifi_kick()` 主动重连 |
| 外网仍不可达 | 每 6 次 | 告警日志 + 再 kick 一次，**不重启** |
| 外网恢复 | — | 发邮件通知，并把当前 IP 带上 |
| IP 变化 | — | 通过所有通道（邮件 + 推送）通知新地址 |

> 「变了才通知」需要跨重启也成立：上次 IP 持久化在 NVS `sms_state/lastIp`，
> 启动时与当前 IP 比对，不同则发「设备网络地址已变化（旧 → 新）」。

检查目标（默认 `www.baidu.com:80`）与间隔可在 `menuconfig` 里改，
避免某些网络访问不了该域名导致误判。

### mDNS 设备发现

IP 由路由器 DHCP 分配，重启/续租都可能变（实测过夜从 `.8` 变 `.6`），
因此设备同时发布 mDNS 记录，提供一个与地址无关的入口：

| 项 | 说明 |
|---|---|
| 设备名 | `sms-<MAC 后两字节>`，例如 MAC `9c:cc:01:c4:9e:3c` → `sms-9e3c` |
| 覆盖方式 | `CONFIG_MDNS_NAME`（menuconfig）；填写时每台必须不同 |
| 发布的服务 | `_http._tcp` 端口 80，实例名 `SMS Forwarder` |
| DHCP 主机名 | 与 mDNS 同名，且在启动 WiFi 前设置，路由器客户端列表里能看到设备名 |
| 冲突策略 | 默认由 MAC 派生，天然唯一；手工同名会互相抢记录，必须在配置上区分 |
| 局限 | 链路本地组播，只在同一二层网段有效；跨网段访问请用 IP |
| 失败影响 | mDNS 初始化失败只记日志，不影响 Web 与短信主流程 |

实现位置：`components/net/src/mdns.c`（命名与发布）、`wifi.c`（DHCP 主机名）。

### 串口互斥与 URC 分发

`at_client` 用一把**递归互斥锁**保护 UART：

- 任何 AT 事务先 `at_lock()`，事务期间读到的非应答行（`+CMT:`、`+CEREG:` …）**入 URC 队列**，不直接回调；
- `at_reader` 任务负责两件事：拿锁读串口 → 入队；然后出队 → 交给 `modem` 的 URC 处理器；
- 也就是说 **URC 状态机永远只有一个消费者（at_reader 任务）**，不会出现“事务上下文里解析到一半、
  另一个任务接着解析”的错位，也避免在持有 AT 锁时做通知等慢操作；
- 队列满（8 条）时退回同步回调，宁可慢也不丢短信；
- 多步操作（初始化、发送 PDU）可以嵌套持锁，保证时序不被打断。

URC 状态机：`+CMT:` → 等一条 PDU。模组常常先把 `+CMT` 报上来，再回当前 AT 命令的应答
（`+CPIN: READY` 之类），PDU 夹在应答后面；所以等待期间只用「纯十六进制、长度 ≥20、偶数位」判定 PDU，
其它行照常按 URC 解析但**不结束等待**，攒满 16 行或 5 秒还没等到才放弃。
实测：短信在 `AT+CPIN?` / `AT+CMGL` 事务进行中到达（`+CMT: ,146` → `+CPIN: READY` → PDU），
仍能被正确解析并转发（旧逻辑会在这里把整条短信丢掉，表现成长短信缺第 1 段）。

## 4. 关键数据流

### 接收短信

```
4G 模组 ──+CMT/PDU──▶ at_reader(modem) ──pdu_decode_deliver──▶ sms_deliver_t
   │                                                              │
   │  长短信？                                                    ▼
   │  └─ sms_assembler（按 ref+sender 聚合，30s 超时）──▶ 完整文本 ──▶ forwarder 队列
   │                                                                  │
   │                                          ┌───────────────────────┤
   │                                          ▼                       ▼
   │                                    黑名单过滤            管理员命令（SMS:/RESET/RESETPASS）
   │                                          │                       │
   │                                          ▼                       ▼
   └──────────────────────────── notify 队列（邮件 + 推送通道）
```

### 发送短信

```
HTTP / 管理员短信
   │
   ▼
modem_send_sms() ──堆作业──▶ modem 队列 ──▶ pdu_encode_submit() ──AT+CMGS──▶ 模组
   │                                          │
   └──── 信号量等待结果 ◀────────────────────┘（ok/失败原因写入同一作业对象）
```

作业对象在堆上分配、以指针入队：工作线程与调用方共享同一块内存，
避免“值传递丢失结果”的经典问题。等待超时时调用方**不会释放作业**（标记 `abandoned`
后交给 worker 回收），从而不会出现 worker 回写已释放内存的悬空指针。

并发语义：多个 HTTP 异步任务可以同时提交 AT 作业，它们按队列顺序串行执行；
任何一个作业都受自身超时约束（`at_command` 有 deadline，初始化最多 3 轮重新上电），
所以 worker 不会被永久占死。

## 5. 内存策略

ESP32-C3 约 300KB 可用 RAM。实测（2026-11）：开机 190KB，WiFi + lwIP + 各任务就绪后稳态 **51~54KB**，
TLS 握手（推送/收发邮件）期间仍有 **20KB 以上**可用。

- `CONFIG_MBEDTLS_DYNAMIC_BUFFER=y`：TLS 收发缓冲按需分配，握手后释放；
- `CONFIG_MBEDTLS_SSL_IN_CONTENT_LEN=8192`：**不能再降到 4096**。服务器常把整条证书链
  塞进一个 TLS 记录，smtp.qq.com 是 5489 字节、百度 4773 字节，4096 装不下会直接握手失败
  （日志 `TLS 握手失败 … tls=0x87`）。8192 覆盖绝大多数站点，代价是每连接多占约 4KB 堆；
- WiFi 动态收发缓冲下调到 4 静态 / 8 动态 RX / 8 动态 TX，比默认 16/16 省出 20KB 以上；
- 日志环形缓冲 200 行 × 192 字节（37.5KB 静态）；
- 首页按 **2KB 块**渲染并 `httpd_resp_send_chunk` 输出，峰值不再需要 40KB 连续内存；
- 网页异步任务默认栈 6KB：C3 的最大连续块常常只有 6~8KB，10KB 栈会让请求直接起不来；
- 长短信合并（最大 5KB）与 PDU 解码结果都在堆上，避免小栈任务溢出。

## 6. 错误处理

| 场景 | 策略 |
|---|---|
| AT 无响应 | 初始化阶段重试 + 重新上电；运行期返回超时并记日志 |
| 网络未注册 | 初始化 30 次 ×1s 轮询后标记 `modem_ready=false`，Web 显示“未就绪” |
| PDU 解析失败 | 记录原始 PDU 并丢弃，不影响后续短信 |
| 长短信缺段 | 30s 超时后按已收分段合并，缺失处标注 `[缺失分段N]` |
| 邮件/推送失败 | 只对「可能没送到」的情况重试：传输层失败（status=0）、5xx、429，最多 3 次；2xx 已送达就不再重试，避免重复通知；其余 4xx 视为配置错误不重试 |
| 短信内容过长 | 编码阶段返回 -2，日志与前端明确提示，不发坏包 |
| HTTP 请求过长 | 长操作走异步处理，httpd 任务继续服务其它请求 |
| HTTPS 握手失败 | 用 CA bundle 正常校验（保留 SNI），配合动态缓冲；见 build-flash.md 第 8 节 |

## 7. Web 界面与配置下发

- 界面是单个 HTML（内联 CSS/JS）随固件嵌入，数据全部走 JSON 接口
  (/config、/status、/log)，因此没有占位符替换，也不会再出现"模板被 CSS 的百分号打乱"的问题。
- 配置模型：推送通道从固定 5 个改为动态数组（默认 5、上限 50、堆上按实际数量分配），
  NVS 用 pushCount 记录数量；老配置键名不变，缺 pushCount 时按已有 pushN* 键推断。
- 变更通知：保存后按分区哈希比对，只对真正变化的分区发一条系统通知；账号/密码变化才提示新密码。
- 路由：共 29 个 URI 处理器，max_uri_handlers 必须不小于该数量（当前 32），
  注册失败会打印日志，避免接口静默 404。
- 页面：概览 / 推送通道 / 设备 / 保号发送 / 后台管理 / 日志 / 关于项目，顺序固定；
  「保号发送」把发短信与 Ping、HTTP 保号操作放在一起，「日志」页同时提供 AT 指令执行；
  「关于项目」页展示项目开源地址（https://github.com/chenxuuu/sms_forwarding）、固件版本、设备型号与设备名。
- 邮件通道可选：`config_mail_active()` = 开关打开 且 SMTP 配置齐全；开关存 NVS `mailEnable`，
  缺键时默认开启，保证老配置升级后行为不变。
- 本机号码：配置项 `self_phone`（NVS `selfPhone`），启动时 `AT+CNUM` 仅在为空时自动补全；
  推送载荷统一带上（文本通道追加一行 / JSON 字段 / GET 参数 / 模版 `{self_phone}`）。
- 未保存保护：编辑推送通道即进入「未保存」状态（底部悬浮保存条 + 卡片内标签），切换页面、
  刷新、关闭标签页都会二次确认；保存邮件/账号等其它分区时不会重载通道，避免冲掉正在编辑的内容。
- 确认框：按钮按具体动作命名（留在此页 / 放弃修改并离开 / 确定重启），主色高亮给安全选项，
  危险动作只用红色描边，避免“确定=保存还是丢弃”的歧义。
